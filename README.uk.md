# gtfs-eta — відкриті фіди реального часу для громадського транспорту Львова

🇬🇧 [English](README.md) · 🇺🇦 **Українська**

Безкоштовні відкриті фіди **GTFS Realtime** для всіх трамваїв, тролейбусів і автобусів Львова. Час прибуття **прогнозує модель машинного навчання**, навчена на місяцях реального руху транспорту. Його не копіюють із розкладу. Ключ API й реєстрація не потрібні.

| | |
|---|---|
| **TripUpdates** (прогноз прибуття) | `https://eta.lad.lviv.ua/feed/trip_updates.pb` |
| **VehiclePositions** (очищені, з прив'язкою до рейсів) | `https://eta.lad.lviv.ua/feed/vehicle_positions.pb` |
| **GTFS static** (розклад перевізника) | `https://track.ua-gis.com/gtfs/lviv/static.zip` |
| Сторінка документації для споживачів (EN/UA) | [eta.lad.lviv.ua](https://eta.lad.lviv.ua/) |
| Перевірка стану | [gtfs-eta.vbhjckfd.workers.dev/health](https://gtfs-eta.vbhjckfd.workers.dev/health) |
| Застосунок для пасажирів на цих даних | [lad.lviv.ua](https://lad.lviv.ua) |

**Точність** (відкладена вибірка, усі горизонти): середня абсолютна похибка **92,8 с**, медіана **45 с**. На 1 / 5 / 10 зупинок наперед MAE становить 61 / 94 / 132 с. Це на 22% краще за попередню модель на одному знімку. [Деталі](#оцінювання).

## Для споживачів фідів

### Швидкий старт

```bash
pip install gtfs-realtime-bindings requests
```

```python
import requests
from google.transit import gtfs_realtime_pb2

feed = gtfs_realtime_pb2.FeedMessage()
feed.ParseFromString(requests.get(
    "https://eta.lad.lviv.ua/feed/trip_updates.pb", timeout=10).content)

for e in feed.entity[:3]:
    tu = e.trip_update
    for stu in tu.stop_time_update:
        if stu.HasField("arrival"):
            print(tu.trip.trip_id, stu.stop_id, stu.arrival.time, "±", stu.arrival.uncertainty, "с")
```

Опитуйте кожні **5–10 с**. Фід оновлюється приблизно кожні 10 с. Edge Cloudflare віддає його з `Cache-Control: public, max-age=3, stale-while-revalidate=2, stale-if-error=60`, тож частіше опитування поверне ті самі байти.

Обидві адреси разом зі static zip підключаються до будь-чого, що розуміє GTFS-RT: OpenTripPlanner, MOTIS, Transitous тощо.

### GTFS static

Розклад — це власний фід перевізника (видавець **Львівавтодор**). Ми його не змінюємо. Фіди реального часу використовують його ідентифікатори без змін, тож об'єднання працюють напряму. Ми перевіряємо його кожні 5 хвилин і переходимо на нову версію приблизно за 30 хвилин після її публікації.

| Файл | Примітки |
|---|---|
| `agency.txt` | Часовий пояс — Київ, записаний як `Europe/Kiev`. |
| `routes.txt` | Близько 70 маршрутів. `route_type` **0 = трамвай**, **3 = автобус *і* тролейбус**. Розрізняйте за коротким номером: `Т…` трамвай, `Тр…` тролейбус, `А…` автобус. |
| `stops.txt` | Близько 1 060 зупинок. `stop_id` — внутрішній ключ, який використовують фіди реального часу. `stop_code` — номер на табличці зупинки, той, що знають пасажири. |
| `trips.txt` | Близько 15 700 рейсів із `direction_id`, `shape_id` і `block_id`. `trip_id` має вигляд `18550_0_1`. |
| `stop_times.txt` | Плановий час для кожної зупинки кожного рейсу (близько 430 тис. рядків). |
| `shapes.txt` | Геометрія маршрутів. У середньому на маршрут припадає 216 рейсів і лише 2,5 різні траси. |
| `calendar.txt`, `calendar_dates.txt` | Дні обслуговування. |

Відомі особливості:

- Тролейбуси мають той самий `route_type` 3, що й автобуси. Якщо потрібен вид транспорту, беріть префікс короткого номера.
- **Автобусний розклад ненадійний.** За живими вимірами відхилення автобусів від розкладу сягає приблизно ±30 хв між 10-м і 90-м перцентилями. Тому модель не використовує жодної ознаки розкладу, а фід публікує `delay` лише для трамваїв і тролейбусів (див. нижче).
- Перевізник перевидає static zip без попередження, іноді посеред дня, і trip_id можуть змінюватися. trip_id у фіді реального часу завжди відповідає версії static, чинній на момент публікації.

### TripUpdates

Один `TripUpdate` на кожен транспортний засіб, прив'язаний до рейсу й на маршруті. Він містить прогнози **щонайбільше на 10 наступних зупинок**.

| Поле | Значення |
|---|---|
| `trip.trip_id`, `route_id` | З GTFS static без змін. |
| `trip.start_date` / `start_time` | Прив'язують оновлення до одного *виконання* рейсу. Самого `trip_id` для цього не досить: кільцевий маршрут повторюється протягом дня, а рейс після півночі належить до попереднього дня обслуговування. |
| `trip.direction_id` | З `trips.txt`. |
| `vehicle.id` | Ідентифікатор транспортного засобу перевізника, той самий, що й у VehiclePositions. |
| `timestamp` | Час **GPS-позиції**, з якої обчислено прогноз. Час у заголовку — це час *публікації*, він завжди свіжий, тож лише це поле відрізняє прогноз із позиції 2-секундної давності від прогнозу з 170-секундної. Позиції, старші за 180 с, відкидаються. |
| `stop_time_update[].stop_id`, `stop_sequence` | GTFS `stop_id`, а не номер на табличці. |
| `arrival.time` | Прогнозований час прибуття, POSIX-секунди. |
| `arrival.uncertainty` | Типова похибка для цього горизонту в секундах, відкалібрована на живих похибках. Для далеких зупинок розширюйте вікно очікування. |
| `departure.time` | `arrival + стоянка`. Стоянку **виміряно**: 32 с для трамваїв і 27 с для автобусів і тролейбусів, за 1,76 млн подій зупинки. |
| `delay` | Відхилення від розкладу, **лише трамваї й тролейбуси**. Для автобусів його свідомо пропущено: споживачі використовують `delay`, щоб екстраполювати зупинки поза списком, а автобусний розклад для цього надто ненадійний. |
| Завершальна зупинка `NO_DATA` | Відгороджує зупинки за межами 10-зупинкового горизонту. Вона називає зупинку, але свідомо не має часу. Без неї специфікація велить споживачам поширити відхилення 10-ї зупинки на решту маршруту. |

Кожне необов'язкове поле **пропускається, а не вгадується**, коли для нього немає вихідних даних. Прогноз, час якого вже минув, публікується як *прибуває зараз*, а не відкидається. Інакше зникло б саме те прибуття, яке пасажир на зупинці чекає найбільше, і зсунулися б номери всіх подальших горизонтів.

### VehiclePositions

Цей фід повторно публікує позиції від перевізника, доповнені тим самим проходом інференсу:

- **Виправлена прив'язка до рейсу**, часто точніша за `trip_id` від перевізника. Кожне виконання рейсу дістається рівно одному транспортному засобу, з `start_date` і `start_time`. Це та сама прив'язка, яку називає TripUpdates, тож два фіди узгоджені.
- Наступна зупинка й `current_status` (`STOPPED_AT` / `IN_TRANSIT_TO`).
- `congestion_level`, обчислений зі співвідношення спостереженої швидкості до історичної для цього маршруту й години.

### Свіжість і стан

- `GET https://gtfs-eta.vbhjckfd.workers.dev/health` повертає JSON із HTTP **200**, коли фід свіжий. Він повертає **503**, якщо фіду понад 180 с, або якщо в години руху немає прогнозів для центральної зупинки (табличка 60, `stop_id` 4577).

  ```json
  {"status":"ok","age_sec":4,"entities":544,"stop_code":60,"arrivals":34,
   "working_hours":true,"vehicles_in":610,"vehicles_stale":20,"feed_skew_sec":3,
   "worker_commit":"a083227","feed_commit":"a083227"}
  ```

- `https://eta.lad.lviv.ua/feed/status.json` — маленький супровідний файл, що оновлюється щонайбільше раз на хвилину, а якщо публікацію заблоковано — одразу. Це дешева перевірка свіжості без розбору protobuf: `feed_timestamp`, `entities`, `vehicles_in`, `vehicles_stale`, `feed_skew_sec`, `published`, `commit`.

## Методологія

Цей розділ — для аналітиків даних і всіх, хто хоче перевірити, чи можна довіряти цим числам.

### Дані

- **Вхід**: GTFS-RT VehiclePositions перевізника (`track.ua-gis.com`), архівовані з червня 2026 року з медіанним інтервалом близько **11 с** між знімками. Архів зберігається як незмінний сирий protobuf (Bronze) у Cloudflare R2.
- **Розклад**: GTFS static з окремою копією кожної версії. Кожен день прив'язано до версії static, чинної того дня (`static/index.json`), тож старі дні розмічаються за правильними трасами.
- **Календар**: прапорці вихідних і державних свят України.

### Розмітка

`run_pipeline.py` перетворює кожен день знімків на навчальні рядки (Gold parquet):

1. Прив'язати кожен транспортний засіб до рейсу (див. [прив'язку до рейсу](#інференс-і-публікація)) і спроєктувати його на трасу рейсу.
2. Знайти **фактичний час прибуття** на кожну зупинку, інтерполюючи спроєктовану відстань уздовж траси між сусідніми знімками.
3. Побудувати рядки, прив'язані до знімків. Кожен знімок транспортного засобу дає по рядку на кожну наступну зупинку, до 10 наперед, з ціллю `seconds_to_arrival`. Оскільки рядки беруться з кожного знімка, а не лише з моментів проїзду зупинок, модель бачить транспорт посеред перегону й на стоянці. Саме тому вона прогнозує ≈0 с, коли автобус уже стоїть на зупинці.
4. Записати добові допоміжні таблиці (`data/training/side/<day>.feed|pos.parquet`): сирі поля фіду кожного транспортного засобу й спроєктовану відстань кожного засобу на маршруті. Тренер відтворює їх, щоб відновити живий стан точно таким, яким його бачила публікація.

Для навчальних рядків береться вибірка з 10% знімків. Допоміжні таблиці повні.

### Модель

**Ціль**: `seconds_to_arrival` — час від знімка до фактичного прибуття на кожну наступну зупинку. Він прогнозується напряму для кожного горизонту від 1 до 10 зупинок наперед.

**Алгоритм** (`live_v2`, [src/train_live.py](src/train_live.py), живі ознаки в [src/live_features.py](src/live_features.py)): `sklearn.ensemble.HistGradientBoostingRegressor` із функцією втрат за абсолютною похибкою. `route_id` і цільова зупинка (топ-254) — нативні категоріальні ознаки, поряд із 13 базовими ознаками й 36 живими стовпцями. Дерева: 255 листків, ≤ 1200 ітерацій, `max_features=0.3`.

**Базові ознаки** — з одного знімка одного транспортного засобу:

| Ознака | Опис |
|---|---|
| `stops_ahead` | Горизонт прогнозу в зупинках (1 = наступна зупинка) |
| `hour` | Часовий контекст |
| `is_weekend`, `is_holiday` | Календарні прапорці (свята України) |
| `remaining_dist_m` | Відстань уздовж траси від спроєктованої позиції до цільової зупинки |
| `progress_speed_mps` | Спостережена швидкість за останній інтервал між знімками (−1, якщо невідома) |
| `stops_remaining` | Скільки зупинок лишається після цільової |
| `trip_progress_frac` | Позиція вздовж маршруту [0, 1] |
| `dist_per_stop_m` | `remaining_dist_m / stops_ahead` |
| `speed_eta_warm` | `remaining_dist_m / effective_speed`; коли швидкість невідома, стартує з апріорної |
| `hist_speed_mps` | Історична медіанна швидкість маршрут×година |
| `hist_travel_time_est` | `stops_ahead ×` історичні секунди на зупинку (з урахуванням стоянок) |
| `stationary_sec` | Секунди відтоді, як засіб востаннє просунувся більш ніж на 25 м |

`apply_priors()` обчислює `speed_eta_warm`, `hist_speed_mps` і `hist_travel_time_est` із таблиці швидкостей і стоянок маршрут×година, побудованої **лише на навчальній частині**, тож витоку з тестової вибірки немає. Жодна ознака розкладу не пройшла відбору ознак.

**Живі ознаки** описують те, що відбувається в мережі просто зараз:

| Група | Стовпці | Джерело |
|---|---|---|
| Живі перегони | `live_path_sec_m3/_m5`, `live_path_cov/_age`, `live_speed_mps`, `cur_link_*` | Останні проїзди кожного перегону між зупинками на шляху **будь-яким** засобом (≤ 30 хв), підсумовані до цільової зупинки |
| Історичні перегони | `hist_path_sec`, `hist_path_sec_dt`, `hist_path_cov` | Медіанний час перегону × місцева година (і × будні/вихідні) за попередні 14 днів |
| Власна історія | `lap_path_*`, `veh_hist_ratio60/_n60`, `own_speed_60/180/300` | Попередній проїзд цим засобом перегонів шляху (≤ 3 год), його власний час проти історичного за останню годину та його нещодавня швидкість |
| Стоянка | `dwell_rem_med/_p75`, `dwell_p_more120`, `dwell_n`, `dwell_long_share` | Залишок стоянки в поточному місці (зупинка + кошик 50 м) з огляду на `stationary_sec`, за зупинками попередніх днів |
| Поля фіду | `pos_age_*`, `fs_now`, `fs_mean60`, `fs_zero_frac600`, `odo_spd_60/180/600/1200`, `odo_m_300` | Вік GPS-позиції, повідомлена швидкість і вікна одометра |

Відсутні живі значення дорівнюють `-1`.

**Один рушій для навчання й публікації.** `LiveState` в обох випадках отримує ті самі два потоки: сирі поля фіду кожного транспортного засобу й спроєктовану відстань уздовж рейсу кожного засобу на маршруті. Тренер відтворює допоміжні таблиці, а публікація подає живий потік. Інформація від інших засобів стає видимою лише на наступному знімку, тож порядок обробки засобів не важить. Це усуває звичний розрив між навчанням і публікацією для живих ознак. Статичні таблиці (історичні медіани перегонів, стоянки) тренер будує з 14 днів до свого останнього дня й вкладає в експорт моделі.

Рядок для публікації збирається **за позиціями**. `build_features` у [src/inference.py](src/inference.py) видає рядки в порядку `FEATURE_COLS` ([src/features.py](src/features.py)). `build_features_live` вибирає з них базові стовпці за індексом (`_LIVE_BASE_IDX`), і цей індекс мусить збігатися з `MODEL_COLS` у [src/train_live.py](src/train_live.py).

### Оцінювання

Порівняння на відкладеній вибірці використовує **поділ за часом**, тож майбутні дані не потрапляють у навчання. Обидві моделі оцінено на тих самих рядках: навчання 2026-09-19..09-30, тест 10-01 чт / 10-02 пт / 10-03 сб, 1,58 млн рядків.

| | один знімок (виведена) | live_v2 |
|---|---|---|
| MAE | 119,3 с | **92,8 с** (−22,2%) |
| медіана | 60,7 с | **45,0 с** |
| p90 | 256,1 с | **192,3 с** (−24,9%) |
| MAE на 1 / 5 / 10 зупинок наперед | 73,8 / 121,7 / 167,9 с | **60,8 / 93,6 / 131,7 с** |

Щоб відтворити:

```bash
python -m src.train_live --train 2026-09-19..2026-09-30 --test 2026-10-01..2026-10-03 --no-save
```

Жива похибка приблизно **вдвічі більша** за офлайн-тестову. Живі прогнози спираються на позиції віком до 180 с, на прогалини у фіді перевізника й на менш певну прив'язку до рейсів. Тому смуги невизначеності беруться з живого оцінювання, а не з тестової вибірки.

**Перенавчання** відбувається щотижня (`retrain.yml`, понеділок 03:00 UTC). Воно розмічає останні ~5 тижнів, навчає на останніх 21 днях із відкладеними останніми 20% і експортує в R2. Демон публікації підхоплює нову модель на наступному перезапуску, без деплою.

### Інференс і публікація

Інференс працює в [scripts/push_feed.py](scripts/push_feed.py). Він використовує компактну реалізацію обходу дерев GBT на чистому Python ([src/inference.py](src/inference.py)), без sklearn і pandas під час виконання.

Кожен цикл (приблизно кожні 10 с):

1. Завантажити VehiclePositions від перевізника. Якщо фіду понад 90 с, узяти останню кешовану копію.
2. **Прив'язати кожен транспортний засіб до рейсу**, оцінюючи відстань до траси, напрямок руху й те, наскільки він відхилявся б від розкладу на цьому виконанні. Виконання з відхиленням понад 1 год не приймається. Рейси розподіляються для всього знімка одразу, тож кожне виконання дістається одному засобу, а другий засіб у «зграйці» бере попереднє або наступне виконання.
3. Для кожного засобу застосувати фільтр сходу з маршруту з гістерезисом, спроєктувати точну позицію на трасу й виміряти швидкість просування порівняно з попереднім циклом.
4. Побудувати рядки ознак для наступних ≤ 10 зупинок і оновити `LiveState`.
5. Запустити серіалізовану модель GBT.
6. Закодувати protobuf TripUpdates і VehiclePositions і завантажити обидва в R2 паралельно, а `status.json` — щонайбільше раз на хвилину.

Прив'язка до рейсу запам'ятовує обхід полілінії для кожної траси. Вона кешує пошук прогресу за розкладом на одну публікацію, бо всі засоби в ній мають спільний `now_sec`. Також вона пропускає будь-яку трасу, чий обмежувальний прямокутник уже дає гірший бал, ніж найкращий повний кандидат. Разом це скоротило повний прохід інференсу з **4,0 с до 0,76 с** на живому парку з побайтно ідентичним результатом. Кеші живуть у словнику завантажених даних, тож застарівають разом з експортом, який описують.

Стан переживає перезапуски: `feed/live_state.pkl.gz` (максимальний вік 3 год) і `feed/tracker_state.json` (максимальний вік 6 год).

### Невизначеність

Кожне `StopTimeEvent.uncertainty` — це **жива** MAE для свого горизонту. `make export` об'єднує MAE за кількістю зупинок наперед з останніх 7 днів архіву якості (`quality/*.json`) і вкладає результат у блоб моделі. Тестова MAE з навчання (`models/uncertainty.joblib`) — лише запасний варіант для холодного старту, поки жоден день ще не оцінено.

### Моніторинг якості наживо

- Кожні 5 хвилин воркер архівує опублікований фід у `predictions/` (зберігається 14 днів).
- `score-quality.yml` (щодня, 02:15 UTC) оцінює вчорашні архівні прогнози проти фактичних прибуттів, отриманих із `raw/`. Він пише `quality/<day>.json`, `latest.json` і `latest.md`: MAE, зміщення й покриття за горизонтами, видами транспорту й маршрутами.
- `pack-raw.yml` (щодня, 04:30 UTC) пакує кожен день `raw/`, старший за 45 днів, в один `archive/raw/<day>.tar.xz` (~8× менший) і видаляє оригінали, щойно завантаження перевірено. `src.snapshots` читає обидві форми.
- `route-mae.yml` (22:00 UTC) відкриває issue з таблицею MAE за маршрутами та її зміною за добу, тож погіршення маршруту видно протягом дня.

## Експлуатація

### Архітектура

```
track.ua-gis.com/vehicle_position  (GTFS-RT)
        │  ~11 с (медіанний інтервал між архівними знімками)
        ▼
  Cloudflare R2 (Bronze)           raw/*.pb  — незмінні знімки protobuf
        │  run_pipeline.py
        ▼
  data/training/YYYY-MM-DD.parquet (Gold)    — рядки зі знімків із фактичними прибуттями
        │  make train
        ▼
  models/eta_live.joblib           live_v2 HistGradientBoostingRegressor
        │  make export
        ▼
  R2: worker/*.pkl                 компактний GTFS + модель для інференсу
        │  push_feed.py (GitHub Actions, кожні ~10 с)
        ▼
  R2: feed/trip_updates.pb         готовий GTFS-RT TripUpdates
      feed/vehicle_positions.pb    очищений VehiclePositions
        │  публічний власний домен R2, кеш на edge
        ▼
  eta.lad.lviv.ua/feed/*  →  споживачі (застосунки, планувальники поїздок, …)
```

Серверів немає. Уся система працює на GitHub Actions, Cloudflare R2 і одному Cloudflare Worker, усе на безкоштовних тарифах.

### Розклади запусків

| Workflow | Коли | Що робить |
|---|---|---|
| `push-feed.yml` | кожні 5 хв, запускає cron воркера | Запускає `push_feed.py --loop 10` приблизно на 5,5 хв. Опитує перевізника кожні 2 с і публікує, щойно позиції змінились, щонайменше раз на 20 с. |
| `refresh-gtfs.yml` | щодня 02:00 UTC і на вимогу | Перебудовує `worker/gtfs_worker_data.pkl` зі `static.zip` перевізника. |
| `score-quality.yml` | 02:15 UTC, запускає cron воркера | Оцінює вчорашні прогнози (див. вище). |
| `retrain.yml` | понеділок 03:00 UTC | Розмічає, навчає й експортує модель. |
| `route-mae.yml` | 22:00 UTC | Відкриває issue з дайджестом MAE за маршрутами. |
| `cleanup-runs.yml` | щодня 03:17 UTC | Видаляє завершені запуски workflow, старші за 2 дні. |

**Трюк із надійним cron.** Заплановані тригери GitHub ненадійні в репозиторіях із малою активністю. Натомість cron Cloudflare Worker спрацьовує кожні 5 хвилин і запускає `push-feed.yml`, тож запуски безшовно перекриваються.

**Оновлення static.** Той самий 5-хвилинний cron робить HEAD на `static.zip` перевізника й запускає `refresh-gtfs.yml`, коли той новіший за наш `worker/gtfs_worker_data.pkl`, з 30-хвилинною паузою (`REFRESH_COOLDOWN_SEC`). Сам лише щоденний cron лишав фід прогнозувати за застарілим static годинами, коли перевізник перевидавав його посеред дня, і кожен перейменований рейс виходив із trip_id, якого в новому static уже не було.

### Запобіжники

- **Сторож фіду.** Між запусками cron будильник Durable Object (`FeedWatchdog` у [worker/worker.js](worker/worker.js)) кожні 30 с робить HEAD на блоб фіду. Якщо 90 с не було жодної публікації, бо запуск помер посеред циклу, він одразу запускає `push-feed.yml`, а не чекає до 5 хвилин. Після кожного запуску діє 180-секундна пауза. Cron перевзводить будильник щоразу, тож ланцюжок сам відновлюється після деплою. Налаштувати чи вимкнути його можна змінними `WATCHDOG_*` у `wrangler.toml` (`WATCHDOG_DISABLED = "true"` зупиняє). Усе, що він використовує, є на безкоштовному тарифі Workers.
- **Захист від обвалу.** Якщо прохід дав менше 30% сутностей попереднього фіду, а в попередньому їх було щонайменше 20, старий фід лишається, і надсилається попередження `FeedCollapse`. Це не дає поганому знімку від перевізника спорожнити фід для всіх споживачів.
- **Застарілі дані перевізника.** VehiclePositions, старші за 90 с, замінюються кешованою копією. Окремі GPS-позиції, старші за 180 с, відкидаються.
- **Відкат моделі.** Кожен експорт, що публікує нові дерева, спершу копіює старі в `worker/eta_pipeline.pkl.prev`. Скопіювавши цей об'єкт назад поверх `worker/eta_pipeline.pkl`, можна повернути попередню модель за один перезапуск демона (близько 5 хв).

### Воркер

[worker/](worker/) — звичайний JS Cloudflare Worker. Він **не** проксіює фіди: їх R2 віддає напряму зі свого власного домену з кешем на edge, тож опитування не коштує ні виклику воркера, ні читання R2. Він обробляє лише:

- `GET /` із браузера (`Accept: text/html`): двомовну EN/UA сторінку документації, [worker/index.html](worker/index.html). Її також змаршрутизовано на `https://eta.lad.lviv.ua/`, лише корінь; `/feed/*` лишається на R2.
- `GET /` від будь-якого іншого клієнта та `GET /vehicle_positions`: **301-редирект** на адреси R2, для зворотної сумісності зі споживачами, які ще не перейшли. Відповіді кореня мають `no-store` / `private`, бо кеш edge розрізняє лише шлях і ігнорує `Vary`.
- `GET /health`: розбирає фід власноруч написаним обходом protobuf (без залежностей) і повертає 200 або 503.
- Cron: запускає workflow, архівує опублікований фід і перевіряє свіжість static.

Спершу це був Python Worker. Ізоляти Pyodide час від часу потрапляли в «отруєний» стан, коли кожен запит падав приблизно за 2 мс ще до коду обробника (шторми `scriptThrewException`), тож його переписали на JS.

### Структура сховища R2 (medallion)

```
gtfs-lviv/
  raw/        YYYY-MM-DD/<feedTsISO8601Z>.pb   # Bronze — незмінний сирий protobuf
  archive/raw/ YYYY-MM-DD.tar.xz              # Bronze після 45 днів, один xz tar на день
  positions/  YYYY-MM-DD.parquet               # Silver — зведені рядки
  static/     <feedVersion>/static.zip         # версії GTFS static
  static/     index.json                       # день → feedVersion
  _meta/      collector_health.json            # лічильники стану збору
  feed/       trip_updates.pb                  # опублікований TripUpdates (eta.lad.lviv.ua)
  feed/       vehicle_positions.pb             # опублікований VehiclePositions (eta.lad.lviv.ua)
  feed/       status.json                      # супровідний файл свіжості
  feed/       live_state.pkl.gz, tracker_state.json   # стан демона між перезапусками
  predictions/ YYYY-MM-DD/<feedTsISO>.pb       # вибірковий архів опублікованого фіду (14 днів)
  quality/    YYYY-MM-DD.json + latest.json/.md # оцінена якість живих прогнозів
  worker/     gtfs_worker_data.pkl             # компактний GTFS для інференсу
  worker/     eta_pipeline.pkl (+ .prev)       # серіалізована GBT для інференсу
```

Повний контракт даних — у [docs/collector_rules.md](docs/collector_rules.md).

### Телеметрія

#### New Relic

Агент New Relic Node APM не може працювати у Worker: він на CommonJS, запускає фонові таймери збору й читає внутрішні механізми Node, яких в ізоляті V8 немає. Тому [worker/newrelic.js](worker/newrelic.js) надсилає власні події напряму в Event API через `fetch`. Без ключа звітування нічого не робить. Помилки йдуть туди ж; Sentry в проєкті немає ніде.

Воркер надсилає три типи подій, усі з тегом `service = gtfs-eta-worker` і позначкою `GIT_COMMIT`:

- `GtfsEtaWorkerHealth`: по одній на кожну некешовану перевірку `/health`, що повторює вердикт (`status`, `ageSec`, `entities`, `arrivals`, `workingHours`, `vehiclesIn`, `vehiclesStale`, `feedSkewSec`, `feedCommit`). Workers Caching кешує відповідь на 5 с, а влучання в кеш воркер не запускає. Кожне поле й так публічне в тілі `/health`. Старі шляхи редиректу свідомо не інструментовано: вони кешуються на edge і сигналу не несуть.
- `GtfsEtaWorkerCron`: по одній на кожне спрацювання cron. Вона записує, який `cron` спрацював, який `workflow` запущено, чи вдалися запуск і архівування фіду, що зробила перевірка свіжості static (`gtfsRefresh`), і `durationMs`. Це єдиний запис про те, що 5-хвилинний конвеєр справді спрацював.
- `GtfsEtaWorkerError`: перехоплений виняток або невдалий запуск workflow, з `level`, `where` (наприклад, `scheduled.dispatch:push-feed.yml`, `watchdog.alarm`, `fetch`), `errorClass`, `message` і `stack`. Вбивство за лімітом CPU сюди не доходить, бо ізолят гине раніше за будь-який обробник; для таких випадків є `wrangler tail`.

Демон публікації звітує так само ([src/nr_events.py](src/nr_events.py), вмикається секретом GitHub `NEW_RELIC_LICENSE_KEY`). Його події мають тег `service = gtfs-eta-daemon` і позначку коміту фіду:

- `GtfsEtaDaemonError`: `level = 'error'` для невдалої ітерації публікації (`errorClass`, `message`, останні 4000 символів `traceback`) і `level = 'warning'` з `errorClass = 'FeedCollapse'`, коли захист від обвалу притримує фід.
- `GtfsEtaDaemonRun`: по одній на кожну задачу push-feed, з `pushes`, `failedPushes` і `durationSec`. Це єдина подія, яку надсилає здоровий запуск, тож вона ж є пульсом демона.

```sql
SELECT max(ageSec) FROM GtfsEtaWorkerHealth TIMESERIES SINCE 1 day ago
SELECT count(*) FROM GtfsEtaWorkerCron WHERE dispatched IS false SINCE 1 day ago
SELECT count(*) FROM GtfsEtaDaemonError FACET level, errorClass SINCE 1 day ago
SELECT sum(failedPushes) FROM GtfsEtaDaemonRun TIMESERIES SINCE 1 day ago
```

Обліковий запис — у регіоні New Relic **EU**. Дані йдуть на `insights-collector.eu01.nr-data.net`, а ключ — це 40-символьний ліцензійний ключ, що починається з `eu01xx`, а не користувацький ключ API `NRAK-...`.

#### Analytics Engine

Ті самі сигнали йдуть і у Workers Analytics Engine через [worker/analytics.js](worker/analytics.js). Це безкоштовно й не потребує ні секрету, ні вихідного запиту. Дані потрапляють у набір `gtfs_eta_worker`. Стовпці позиційні: `index1` — тип точки, `blob1` — коміт воркера.

| `index1` | blobs | doubles |
|---|---|---|
| `health` | `blob2` status, `blob3` feedCommit | `double1` httpStatus, `double2` ageSec, `double3` entities, `double4` arrivals, `double5` workingHours, `double6` vehiclesIn, `double7` vehiclesStale, `double8` feedSkewSec |
| `cron` | `blob2` cron, `blob3` workflow, `blob4` gtfsRefresh | `double1` dispatched, `double2` archived, `double3` durationMs |
| `watchdog` | `blob2` action (`ok`/`cooldown`/`dispatched`/`dispatch_failed`/`error`) | `double1` вік фіду (ageSec), `double2` dispatched |

Невідомі числа записуються як `-1`. Запитуйте через SQL API з токеном API, що має право *Account Analytics: Read*:

```sql
-- втручання сторожа за годину
SELECT toStartOfHour(timestamp) AS h, count() AS n
FROM gtfs_eta_worker WHERE index1 = 'watchdog' AND blob2 = 'dispatched'
  AND timestamp > NOW() - INTERVAL '1' DAY GROUP BY h ORDER BY h
-- найбільший вік фіду, який бачив сторож, за 5 хв
SELECT toStartOfFiveMinutes(timestamp) AS t, max(double1) AS max_age
FROM gtfs_eta_worker WHERE index1 = 'watchdog'
  AND timestamp > NOW() - INTERVAL '1' DAY GROUP BY t ORDER BY t
```

```bash
curl "https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT_ID/analytics_engine/sql" \
  -H "Authorization: Bearer $CF_API_TOKEN" --data "SELECT ..."
```

### Смоук-тести

```bash
make smoke
# або
pytest tests/test_smoke.py -v
```

Тести звертаються до живого фіду через мережу й перевіряють:

- HTTP 200 і тип вмісту `application/x-protobuf`
- Фід розбирається як коректний `FeedMessage`, а його час свіжий
- Усі сутності — `TripUpdate` з коректними послідовностями зупинок
- Час прибуття монотонно зростає й лежить у майбутньому
- Кожен TripUpdate має `timestamp` прогнозу
- Огорожа горизонту `NO_DATA`, якщо є, стоїть останньою, називає зупинку й не має часу
- trip_id відповідають львівській схемі `DIGITS_DIGIT_DIGIT`
- stop_id числові
- Покриття транспортних засобів ≥ 50% від фіду VehiclePositions перевізника
- Перетин рейсів із власним фідом `trip_updates` перевізника ≥ 10%

Інша цільова адреса:

```bash
SMOKE_URL=https://your-preview-url.workers.dev make smoke
```
